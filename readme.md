# ミニマル株価売買ゲーム『URIKAI』開発コンテキスト・議論の全履歴

本書は、インディーゲーム『URIKAI』の開発において、人間とAIの間で行われた議論の全容、仕様の変遷、および最終決定された設計を網羅したドキュメントである。Cursorが実装を行う際、「なぜこのコード（仕様）になっているのか」の背景を正しく理解し、勝手な機能追加（アイデアの先祖返り）を強力に防止するために使用する。

---

## 1. プロダクトの絶対理念

- **1画面・1ボタン・1分**：投資の勉強やシミュレーションではなく、チャートの波にタイミングを合わせる音ゲーや落ち物パズルに近い快感を狙う。
- **徹底的な引き算**：数量入力、銘柄選択、レバレッジ、ゲーム内通貨、ショップ、ガチャといった複雑な要素はすべて排除する。

---

## 2. 議論の軌跡（提案・課題・解決策の全履歴）

開発を進める上で発生した重要な課題と、それをシンプルなルールのままクリアした解決の歴史である。

### ① 売買ボタンの構成

**初期案**：画面下部に【BUY（全力買い）】と【SELL（全力売り）】の2つのボタンを並べる。

**課題**：現金を持っている時は【SELL】を押しても意味がなく、株を持っている時は【BUY】を押しても意味がない。常に50%の確率で無効なボタンが画面に見えているのはUIのノイズであり、押し間違いのストレスを生む。

**確定解決策**：ボタンを1つに統合する。画面下部を丸ごと占める巨大な「1つの可変ボタン（トグル式）」にする。

- 現金保有時：🔴 【BUY（全力買い）】
- 株保有時：🔵 【SELL（全力売り）】
- 注文中（ラグ）発生時：🔘 【注文中...】（グレーアウト・タップ不可）

### ② 注文の遅延（ラグ）の扱い

**初期案・提案**：ボタンを押してから確定するまでに現実のような「遅延（ラグ）」を発生させ、その遅延を短くできる「プレイヤー強化（パラメータ育成）要素」を入れる。

**課題**：育成要素を入れると、ショップ画面、ゲーム内通貨、強化素材などのシステムが芋づる式に必要になり、アプリのシンプルさが崩壊する。

**確定解決策**：パラメーター強化は見送る。遅延は「0.5秒〜1秒の完全固定」とし、「遅延（慣性）そのものを予測して一歩手前でボタンを押すプレイヤースキル」へと昇華させる。

### ③ 実在データの流用と「ハズレ回」「覚えゲー」問題

**提案**：過去の実在する有名銘柄（ビットコインやAppleなど）のチャートを60秒に圧縮して使い、最後に正体を明かす。

**課題A（ハズレ回問題）**：「買いしかできない」仕様において、ただの暴落や横ばいのチャートが来るとプレイヤーは稼げず、ただのストレス（ハズレ回）になりリセマラを誘発する。

**課題B（覚えゲー問題）**：何度も遊ぶうちにチャートの形（波形）を暗記してしまい、ハラハラ感が消える。

**確定解決策（Aへの対策）**：単なる暴落や横ばいは不採用とし、実在データから「3つのドラマチックな感情パターン」の期間だけをトリミングして厳選する（初期ボリュームは計30本）。

- **暴落×反発（V字）**：底値を見極めて逆張りする脳汁体験。
- **横ばい×乱高下（ギザギザ）**：数秒おきに短期売買を繰り返すアクション性。
- **高騰×バブル崩壊（チキンレース）**：どこで逃げるかの恐怖との戦い。

**確定解決策（Bへの対策）**：チャートデータを実際のゲーム時間（60秒）より10秒長い「70秒分」で保持し、ゲーム開始時に「0〜10秒の開始オフセット（切り出し位置）」をランダムにずらす。これにより、形状の嘘をつくことなく、暴落や高騰のジャストタイミングが毎回数秒ずれるため暗記を完全に防止できる。

### ④ チャート描画と視覚的UX

**課題A（Y軸のスケーリング問題）**：後半に10倍に爆上がりするチャートの場合、全体の最高値・最安値に合わせて縦軸を固定すると、前半の細かな値動きが画面上で「完全な真横の一本線（平ら）」に見えてしまいプレイ不能になる。また、先の展開のネタバレになる。

**課題B（描画のカクつき）**：1秒刻みのデータをそのまま「カクン、カクン」と更新すると、0.5秒のラグの滑るような生々しさが伝わらない。

**課題C（画面酔い）**：Y軸をリアルタイムに変えると、急騰時にグラフがガクガク伸縮して画面酔いを起こす。

**確定解決策（Aへの対策）**：画面には「過去20秒間の値動き」だけを表示するウィンドウ追従（左スクロール）方式とする。

**確定解決策（Bへの対策）**：データは1秒刻みだが、画面上では線形補間（Linear Interpolation）を用いて、毎秒、線が右へ滑らかに伸びていくアニメーションを行う。約定はボタンを押した瞬間のミリ秒単位の座標で判定する。

**確定解決策（Cへの対策）**：Y軸の上下幅（今画面に見えている20秒間の最高値・最安値）が更新される際、0.2秒ほどかけてニュッと滑らかにズームイン/アウトする補間処理を入れる。

### ⑤ 評価軸とリプレイ性

**課題A（スコア格差）**：シナリオによって「理論上稼げる限界の金額」が全く異なるため、最終金額だけで競わせると、上限の低い「乱高下シナリオ」がハズレ回扱いされる。

**課題B（タイムアップ時の理不尽）**：残り59.8秒でSELLを押した場合、0.5秒のラグのせいで約定前にタイムアップとなり、株を持ったまま終了して理不尽な損失になる。

**課題C（すぐ飽きる）**：1分で終わるため、やり込み要素がないとすぐ消される。

**確定解決策（Aへの対策）**：金額評価ではなく、そのチャートで完璧に売買した場合の理論最大資産を裏で算出し、プレイヤーがどれだけ肉薄できたかという「スコアシンクロ率（％）」を最終評価の軸とする。

**確定解決策（Bへの対策）**：60秒のタイムアップを迎えた瞬間、持っている株は強制的にその時点の価格で全売却（自動大引け精算）される一律のルールとする。

**確定解決策（Cへの対策）**：複雑な育成ではなく、一度クリアして正体が明かされた銘柄がカラーで解放され、自己ベストシンクロ率が1行だけ記録される「歴史スクラップ図鑑（1画面のみ）」を裏に用意する。

### ⑥ SNSシェアとネタバレ

**課題**：プレイヤーが終了画面のチャート形状をそのままSNSにスクショ投稿すると、未プレイユーザーへの「答え合わせ」になり、アプリの寿命を縮める。

**確定解決策**：SNSシェア用の自動生成テキスト（またはOGP画像）には、チャートの形状（折れ線）は絶対に載せない。テキスト（銘柄名、最終資産、シンクロ率、称号）とランクバッジなどの装飾のみにする。

## 3. 最終確定した基本設計仕様

### UI State の完全固定定義

データ構造の肥大化を防ぐため、アプリは以下の6つの基本変数のみで状態を管理する。

```kotlin
data class GameUiState(
    val gameState: GameState,       // START / PLAYING / RESULT
    val currentSecond: Int,         // 0〜59秒のタイマーカウント
    val currentPriceDisplay: Int,   // 画面に表示する現在の擬似株価（初期値1000ベース）
    val totalAsset: Int,            // 現在の総資産（初期値: ¥10,000）
    val hasStock: Boolean,          // 株を保有しているか（trueならSELLボタン、falseならBUYボタン）
    val isOrderProcessing: Boolean  // 注文中（ラグ）フラグ（trueならボタンをグレーアウトし無効化）
)
```

※表示株価の工夫：CSVの比率データ（初期値100）をそのまま出すと数学のグラフに見えて冷めるため、画面上は一律「初期株価 ¥1,000」に擬似変換して親しみやすさを出す。

### データ構造（CSV仕様）

#### 編集用（正本）— `content/`

表示名・史実コメント・形状は **`content/` 配下を編集**する。手順は `content/README.md` を参照。

| ファイル | 内容 |
| --- | --- |
| `content/stages_meta.csv` | 1ステージ1行（名称・期間・ヒント・史実コメント・seed） |
| `content/keyframes.csv` | 形状の制御点（`stage_id, second, price_ratio`） |

生成コマンド: `py -3 tools/generate_charts_csv.py`

#### 実行用（生成物）— `app/src/main/assets/charts.csv`

アプリが読み込む縦持ちCSV（**手編集しない**）。

| カラム | 型 | 説明 |
| --- | --- | --- |
| `stage_id` | String | ステージID |
| `brand_name` | String | 銘柄・事件の正式名称 |
| `period` | String | 歴史的な時期 |
| `scenario_type` | String | `V_SHAPE` / `ZIGZAG` / `BUBBLE` |
| `hint_text` | String | 開始3秒間のアシストテキスト |
| `history_comment` | String | クリア後・図鑑の史実1行 |
| `second` | Int | 0〜69秒（計70秒分） |
| `price_ratio` | Float | 開始時を 100.00 とした相対比率 |

## 4. 開発ロードマップ

### Phase 1：骨組み（完全なステートマシンの構築）

- **ゴール**：画面タップで「BUY/SELL」状態が切り替わり、60秒でゲームがカチッと停止すること。
- **注意**：チャートは描画しない（ただの直線かダミーの数字でよい）。画面レイアウトとタイマー、ボタン無効化ロジックの骨組みだけを完璧にする。

### Phase 2：手触り（描画と慣性の実装）

- **ゴール**：1本のCSVデータがパースされ、線形補間によって滑らかに右へ伸び、ズームイン/アウトと0.5秒のラグが最高に気持ちいい状態を作ること。

### Phase 3：ゲーム性（30銘柄と評価ロジック）

- **ゴール**：30本の本番データを流し込み、60秒時点での強制自動精算、および「理論上最大値」に対する「シンクロ率（％）」の計算ロジックを完成させ、ゲームとして遊べる状態にすること。

### Phase 4：装飾・完成（ビジュアルとコレクション）

- **ゴール**：ピッチブラック背景にシアン/マゼンタのネオンラインが走るサイバーパンク風のビジュアル調整、売買時のSE、1画面きりの「歴史スクラップ図鑑」を実装し、製品として完成させる。

## 5. Cursorへの注意書き（ガードレール）

- **段階的ロックの遵守**：現在指定されているPhase以外のコードは、たとえ1行であっても、見栄えを良くするためであっても絶対に先走って書いてはならない。
- **提案の禁止**：`GameUiState` の拡張や、新しいボタン、別画面の追加を自発的に提案・実装してはならない。仕様に忠実に、極限のシンプルさを維持すること。
